# notes — 决策记录

本目录记录**决策**:为什么这么做、放弃了什么、怎么算做完。一件事一个文件。

**路径双轴:目录即状态,子目录即分类。** 空白上下文的 agent 看路径就知道时态与性质,不必读完全文再猜:

```
.agents/notes/proposed/<kind>/     打算做,还没做(或只做了一部分)
.agents/notes/implemented/<kind>/  已经做完,文件描述的是现在的现实
.agents/notes/rejected/<kind>/     想过,决定不做,理由写在状态行
.agents/notes/archived/<kind>/     做完且已过时,封存冻结(manifest 校验)
```

## 文件怎么写

文件名 `yyyy-mm-dd-<标题>.md`,放在 `{lifecycle}/{kind}/` 下。日期是**第一次提出**的时间(查 git 史),不是完成时间;之后无论状态怎么变,文件名不改——按文件名排序就是提出顺序。

开头四行固定:

```markdown
# 决策记录: <标题>

Status: proposed
```

第 1 行标题,第 2 行空,第 3 行状态,第 4 行空。状态只有四种写法,且**必须和所在目录一致**:

- `Status: proposed`
- `Status: implemented`
- `Status: rejected — <一句话说明为什么不做>`
- 归档件保持 `Status: implemented`,下一行写 `Archived: YYYY-MM-DD`(由归档动作插入,见下)

只有「不做」这一种在状态行里带内容,因为读者点开一篇被否决的记录,最想知道的就是为什么否。

## 分类(kind)

| kind | 装什么 |
|---|---|
| `feature` | 新能力:此前做不到、现在能做的事 |
| `bug-fix` | 缺陷:行为与预期不符的修复及其复盘 |
| `simplification` | 只删不加的简化 |
| `architecture` | **发布的源码/产物本身**的结构决策 |
| `process` | 代码**周围**的工具、政策、工作流 |
| `testing` | 测试基建 |

划界句:**architecture 是「我们发布的东西」的结构,process 是「围绕它的工具与规矩」**。`refactor` 有意不设——与 simplification 重叠。分类拿不准时,问「这条决策改的是产物还是流程」。

禁止 `INDEX.md` 之类的集中索引——浏览目录树或全仓搜索。

## 正文骨架

第一节固定是 `## 问题`。之后按状态不同:

**打算做的(proposed)**

```
## 问题              现状是什么,为什么值得动
## 提案              打算怎么做。也可以是「推迟,理由是……」
## 考虑过的其他做法    必须有。每条写清优点和缺点
## 怎么算做完         验收标准
## 风险              可选。做的代价、不做的代价
```

**已经做完的(implemented)**

```
## 问题              当初的问题
## 决定              **用现在时写现在是怎样的**
## 考虑过的其他做法    必须有
## 后果              这个决定带来了什么,包括代价
## 怎么验证的         测试、检查、实测证据。可选
```

**决定不做的(rejected)**:保持它被否决时的样子,冻结。理由在状态行上。

**从「打算做」变成「做完了」要重写时态**——挪目录不是改一行字:「提案」改写成「决定」(现在时,不写「将会」);「怎么算做完」和「风险」折进「后果」;删掉所有计划、清单、待办。检查脚本会拒绝已完成的记录里出现提案期的小节名(行首锚定)。

## 必须写「考虑过的其他做法」

这是唯一被强制的内容项:半年后有人想推翻这个决定,他需要知道当初有没有想过他现在想到的那条路、为什么没走。唯一的例外:本规则生效前(2026-08-26)写的旧文件,替代方案确实无从追溯,可携带精确注释 `<!-- agent-note-format: alternatives-not-recorded (pre-format Agent Note) -->` 替代。

## supersession:笔记永不被改写成另一个决策

- **每篇新笔记动笔前先查旧账**:同一决策已有旧记录——新部分取代旧的就互链;新记录完全吸收旧的,才可删旧,且旧篇独有的理由要先搬进新篇。查都不查就写,是同一件事长出两篇各说一半的根源。
- **已完成的记录要跟上现实,但不许改立场**:被记录的事实变了(路径、默认值、机制),同一次改动里原地改齐,不追加变更史;决策或理由被推翻,写新笔记 supersede 并交叉链接,旧笔记不动。
- **每篇新笔记触发一次 supersession 检查**:它是否取代了某篇活跃记录?被取代的记录要么更新互链,要么按归档/删除规则处置。

## 什么时候归档、什么时候删

判据只有一条:**这篇的理由还能不能指导未来的工作**。字数、年头、目录厚薄都不是判据,不为凑数量归档。

- **implemented → archived**:决定已彻底落地、理由不再指导未来。归档动作只有四种:整文件迁入 `archived/{kind}/`;在 `Status: implemented` 下一行插入 `Archived: YYYY-MM-DD`;同一改动里修好指向它的引用;跑 `npm run verify-archived-agent-notes --write` 把 sha256 封存进 `manifest.json`。**此后正文一个字不再动**——归档是冻住的历史,不是现行的权威;可以链接进去,结论以现行记录为准。
- **rejected 的去留**:还拦得住「诱人但确实错」的念头就留;没人会再提了就整篇删掉,指向它的引用一并处理。
- **proposed 永不归档**:过时的提案改判 rejected,理由写诚实。把「还没做」的东西冻成历史,是在误导后来者。

## 什么时候写一篇

方向性的决定,无论做还是不做,都写。具体标准由项目自己的 `AGENTS.md` 定。纯机械的改动不写:改错别字、调格式、重命名一个变量。

另一类触发:**复盘**。出了同时满足三个条件的 bug——机制不明显(细心的人也会再踩一遍)、逃逸原因是流程缺口而不是孤立笔误、重新发现一遍代价高——写一篇 `bug-fix` 的 implemented 记录,标题前缀「复盘:」,正文回答两问:当时每一道防线为什么都没拦住、加了什么护栏让同类 bug 下次一出现就大声失败。三条件不齐的 bug 不写,一行修掉的进 ops-log / commit message 就够。

## 引用要可检查

提到另一篇记录或另一份文档时,写**相对 markdown 链接**(不写裸文字、不写编号)——记录会在目录之间搬家,真实路径能被 `verify-md-links` 抓住,「某篇」式的引用无人能修。挪动一篇记录,同一改动里修好所有指向它的链接。

## 和 docs/ 的分工

- **`docs/`**——现在是怎样的。给人读的说明书,也给别的 agent 读。**不写变更历史**,不出现「以前」「现在改成」。
- **`.agents/notes/`**——为什么是这样的。决定的理由、放弃的方案、付出的代价。

同一件事两边都会提到,但角度不同:`docs/` 说「这个功能这样用」,notes 说「当初为什么选它而不选另一个」。

## 检查

门禁脚本在仓根 `scripts/`(TS + tsx,lefthook 挂 pre-commit 自动跑;clone 后 `npm install` 完成挂载):

1. `verify-agent-note-classification`——路径必须是 `{lifecycle}/{kind}/`,kind 在六类闭集内,文件名 `yyyy-mm-dd-*.md`
2. `verify-agent-note-format`——头三行骨架、状态行语法、每生命周期必需节、implemented 禁提案期节、「考虑过的其他做法」强制(或祖父注释,仅 2026-08-26 前的旧件)
3. `verify-archived-agent-notes`——归档区结构、`Archived:` 行、manifest sha256 封存 append-only;`--write` 封存新件
4. `verify-md-links`——全仓相对链接与锚点死链(archived 的出链除外)
5. `verify-doc-refs`——TS 源码注释里引用的文档路径存在

手动跑:`npm run verify:notes` 与 `npm run verify:docs`。它们只验骨架,不管文章写得好不好——那是人的事。故意验得少:验得越多越容易逼出凑数的内容。
