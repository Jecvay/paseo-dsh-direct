# 决策记录: 检测 dsh 新版本并验证兼容性

Status: implemented

## 问题

dsh 预发布频繁，依靠人工发现新版本容易遗漏。GitHub Release 也不代表 npm 依赖已经发齐：2026-09-28 的 `0.2.0-rc.1` 已有 Release，但依赖 `@deepseek-ai/dsh-client-ui-settings-account@0.2.0-rc.1` 缺失，实际安装报 `ETARGET`。

## 决定

版本发现与隔离预检由用户授权的黑伤长期管线承接，复用现成 command、事件去重、串行组和人工卡片，不恢复项目旧接单器。GitHub 检测 Paseo/DSH 新 Release；npm 检测发布组合，先解析完整依赖闭包，再隔离安装精确版本、运行实际 fixture。相同组合与等价结果去重，无变化不调用模型。

检查按用途分别给出通过、失败或未知：xmdsh 验证真实 PTY 首句，Paseo 验证官方 manifest build、daemon、插件与模型目录，并以实际会话证据检验多轮和恢复。探针遗漏准备步骤、硬编码模式、环境或网络受阻归未知，不能自动派成插件回归。未知有界退避，持续受阻再请用户判断。

需要插件修改时，通过 [Paseo 跟进手册](../../../skills/paseo-followup/SKILL.md) 进入既有 issue-handler，先查对应问题与候选，再自主调查、编码、review 和测试。跨 `major.minor` 需评估版本线与兼容影响；不因上游发版就提高依赖下限或发包。正式发布及触发发布的合并仍须本人批准当前候选，遵守 [项目发布要求](../../../../AGENTS.md#日常-ops)。管线不升级用户正在使用的 CLI、daemon 或插件。

## 考虑过的其他做法

- 只盯 GitHub Release：有发布说明，但不能证明 npm 依赖齐全，仍需实际安装。
- 发现版本直接更新并发布插件：可能发布未经验证的组合，也不符合逐次确认要求。
- 维持人工发现：没有运行成本，但容易遗漏，无法持续记录组合结果。
- 每轮叫模型查所有上游：无变化仍花额度，因此使用确定性检测。
- 在本仓重建长期控制器：重复黑伤已有调度与续办能力，因此这里只保留业务技能。

## 后果

检测、隔离安装与结果记录已接入；这不代表所有组合通过，也不替代 [完整 Alpha 验收](../../../../docs/alpha-acceptance.md)。真实模型、移动端 UI、全部工具与长期会话仍需独立验证。Paseo 多轮与 reload 证据不足时保持未知，不用“插件 running”推断会话兼容。历史对象不批量开工；候选发布仍逐次确认。

## 怎么验证的

2026-11-08 隔离实测覆盖 DSH `0.2.1-rc.5` 和 `0.2.2-rc.1`，配 pi-tui `0.5.5`、Paseo `0.15.3`、本插件 `0.2.16`。完整安装、版本、DSH 家族包与必要 native import 通过。rc.5 的 PTY 首句 fixture 通过，但退出有 closed-handle/retire 警告，未证明持久化；rc.1 的 TUI 创建会话失败，不能称该组合可用。

Paseo 官方构建准备、隔离 daemon、插件 running 和 fixture 模型目录通过；三轮对话与 reload 仍未知。跳过官方构建造成缺 generated 文件，以及探针强写 mode 的失败，均纠正为探针假设问题，没有创建真实插件工单或发布。事件路由已预演，自然 GitHub 检测 #11 零事件成功；本人批准后的真实 Publish 全链路未演练。部署入口预演曾误派无对象任务 #12，已停止、修复参数引用并恢复管线，无可见 GitHub 写入；该事故不作为业务交付验收成功。
