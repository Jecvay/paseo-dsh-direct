# 决策记录: 在 Paseo 设置页管理子代理模型

Status: implemented

## 问题

DSH 的子代理选模默认关闭，开启后要求精确的 provider/model 列表。Paseo 用户需要编辑 YAML 才能使用，且模型列表与提供方配置重复维护。用户要求在插件页面选择模型，并在首次初始化时选中当前全部模型。

## 决定

插件设置页直接读写 DSH 原生 `subagent-model-selection-settings`。新增两个桥接方法承载读取与保存，JSON-RPC 帧格式和版本保持不变。插件不持久化第二份模型列表。

首次桥接初始化时，只有原始有效配置缺少开关与列表两个字段，才将成功读取到的全部模型保存并开启选模。显式关闭和空列表均视为用户选择。目录为空时不初始化；部分提供方失败时选择成功返回的模型并在页面提示。后续新增或恢复的模型须手动选择。

每次设置 RPC 启动短期桥接。跨进程使用配置内容及配置源身份的 hash 检查草稿，实际写入仍使用当前 DSH 进程的 revision，由 DSH 文件锁保护。不把 DSH 进程内的数字 revision 当作跨进程版本号。

[profile 选择决定](../process/2026-09-26-drop-pi-tui-dependency.md)继续负责模型路由、默认模型与权限设置。本决定仅为子代理选模引入原生设置写入。

## 考虑过的其他做法

- 在 Paseo 设置中保存另一份列表，再通过启动 patch 覆盖 DSH：实现简单，但两个界面会显示不同选择，也无法明确哪份配置生效。
- 每次启动自动选择所有模型：无需维护，但会撤销用户取消勾选的决定，且不符合仅首次默认全选的要求。
- 长期保留设置桥接进程：能复用数字 revision，但增加闲置进程和生命周期管理；短期桥接加内容 token 已足够。
- 直接修改 YAML：绕过 DSH 的 schema、overlay 检查和文件锁，无法可靠保护并发编辑。

## 后果

用户可搜索、全选、清空和逐项选择，无需手写列表。设置只影响支持选模的 preset 的新会话，已有会话策略由 DSH 保留。新增模型不会自动加入；目录部分失败时必须重试后手动选中恢复的模型。

Paseo UI 使用宿主提供的 TanStack Query，包中只增加开发依赖。DSH 内部 helper 只通过类型引用共享设置契约，不引入 Paseo 运行时。

## 怎么验证的

单元测试覆盖首次初始化、显式关闭、空目录、部分目录失败、跨桥接 token、并发编辑与配置源切换。隔离的真实 DSH 测试验证持久化、重启保留、过期草稿拒绝及旧会话策略保留，不调用模型、不写用户真实 profile。
