# 决策记录: 检测 dsh 新版本并验证兼容性

Status: proposed

## 问题

dsh 预发布频繁，依靠人工发现新版本并发起兼容性检查容易遗漏。

上游存在 GitHub Release 不代表 npm 包已经能安装。2026-09-28 的 `0.2.0-rc.1` 已发布 Release，但其依赖的 `@deepseek-ai/dsh-client-ui-settings-account@0.2.0-rc.1` 未发布，安装时报 `ETARGET`。因此版本检测必须包含实际安装验证。

## 提案

保留版本检测与兼容性验收的需求，具体调度和任务执行方式待定。本提案不指定接单系统，也不授权启动服务。

1. 检测 npm 上的 dsh 新版本，按版本记录检查结果，避免重复报告。
2. 在隔离环境验证版本及其依赖能否安装。缺少依赖时列出包名，不把该组合标为可用。
3. 安装成功后，按 [Alpha 验收规范](../../../../docs/alpha-acceptance.md) 运行兼容性检查。区分通过、失败和未验证项，形成可审查的报告。
4. 同一 `major.minor` 内按现有插件线验证；跨 `major.minor` 时另行评估版本线和兼容性影响。
5. 必要时准备修复和发布材料。每次正式发布或会触发发布的合并，都遵循 [项目发布确认要求](../../../../AGENTS.md#日常-ops)，取得用户对本次发布的明确同意后再执行。

## 考虑过的其他做法

- 只盯 GitHub Releases：能看到发布说明，但不能证明 npm 依赖已经齐全；可以附作参考，仍须实际安装验证。
- 发现版本后直接更新并发布插件：省去人工跟进，但缺少完整验收时容易发布不可用的组合，也不符合本项目逐次确认发布的要求。
- 维持人工发现：没有额外运行成本，但容易遗漏，不能持续产出兼容性报告。

## 怎么算做完

- 检测到一个新版本后，能产出包含安装结论和兼容性检查结果的报告；同一版本不会重复报告。
- 依赖缺包、安装失败及验收未完成时，报告说明具体原因，不宣称该版本已获支持。
- 检测和执行可以停止，停止后不再启动新任务。
- 自动检测与正式发布分别授权，不因发现同线版本而自动合并或发布。

## 风险

npm registry 暂时不可用时，需要保留失败原因并等待后续检查，不能据此判断版本不存在或依赖永远缺失。验收尚未覆盖的交互能力须明确标为未验证。
