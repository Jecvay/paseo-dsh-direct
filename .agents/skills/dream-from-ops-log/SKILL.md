# dream-from-ops-log：把操作日志蒸馏成长期知识

`.agents/ops-log.md` 是临时材料，不是长期文档。它只暂存 git 和流水线都查不到的事件：手工部署与回滚、外部服务配置变更、真实运行与生产实测、跨仓协调。这个技能把这些事件里还有用的部分变成长期知识，然后把日志清空。

日志本身会越写越像流水账：一次性命令、失效的版本号、已经没有参考价值的排障过程。直接留着，后来的人分不清哪条现在还成立；所以蒸馏的产出必须离开日志，落在能表达「现在怎样」或「为什么这样」的地方。

## 流程

### 1. 读全量日志并分条

先通读 `.agents/ops-log.md`。把每个日期条目拆成独立事实，标上它属于哪类：

| 类别 | 处理 |
|---|---|
| `docs/` 或笔记已经写过的 | 丢弃，重复内容不进长期文档 |
| 现在仍然成立、但没写过的操作事实 | 蒸馏，落 `docs/` |
| 一个决定及其理由、放弃的方案、代价 | 落 `.agents/notes/`，按 `{lifecycle}/{kind}/` 归档 |
| 反复用到的固定流程 | 落 `.agents/skills/<name>/`，或补进已有 skill |
| 一次性事件：某次发布的具体版本、某台机器的 PID、临时路径、已停用的服务 | 丢弃 |
| 结论可能已经过时的观察 | 先核实，再决定 |

判断「是否已经写过」要真的去搜，不要凭印象。搜索范围至少包括 `docs/`、`.agents/notes/`、`AGENTS.md`、`.agents/skills/`。

### 2. 核实，不把历史观察当现行事实

这是这个技能里最容易出错的一步。日志写的是「当时看到的现象」，`docs/` 要求写「现在生效的机制」。两者之间可能已经变了：上游升级、代码重写、配置改过、服务停用。

对每条准备落进 `docs/` 的结论，至少做一次核实：

- 行为类结论 → 读当前实现或跑一次最小验证；
- 版本、路径、命令 → 查当前仓库和当前安装；
- 上游接口 → 查当前依赖版本或官方文档。

核实不了，就不要写成现在时。留在报告里说明「未能核实」，或者写进笔记时明确标注这是当时的观察。

日志里常见的旧痕迹不要带进文档：本机用户名和绝对路径、会话 UUID、进程号、某次发布的 commit 哈希、已删除目录、个人凭证位置。

### 3. 选落点

按 `AGENTS.md` 的落点规则：

- **现在怎样** → `docs/`。用户手册、排障步骤、环境要求写这里，保持现在时，不写「以前如何」。
- **为什么这样** → `.agents/notes/`。决定的理由、放弃的方案、付出的代价。方向性决定才写，纯机械经验不写。
- **可复用流程** → `.agents/skills/`。只有确实会被反复执行、且有明确步骤和判断标准的，才值得做成 skill；一次性排障过程写进 `docs/` 的一节更合适。

宁少勿多。日志里十条事件可能只值得写两段文档。把流水账搬进 `docs/` 只是换了个地方变旧。

### 4. 写，然后过门禁

改动尽量小，补在已有章节里，不新开文件除非确实需要新主题。新增 `docs/` 文件时同步更新 `docs/README.md` 与 `docs/README.zh.md` 的索引。

写完跑：

```bash
npm run verify:notes
npm run verify:docs
```

门禁失败先修好，不要带着死链清空日志。

### 5. 清空日志

所有条目都处理完、门禁通过之后，把日志重置成只剩标题和说明的空文件：

```markdown
# 待蒸馏的仓外事件

仅暂存 git 与部署流水线无法还原的手工部署、配置变更和真实运行证据。不记录仓内代码改动，不包含凭证或完整对话。运行 dream-from-ops-log 完成蒸馏后清空本文件；长期文档不要把这里作为证据链接。
```

如果蒸馏期间日志又多了新条目（别的会话在同时写），保留这些新条目，只清掉这次处理过的部分；无法可靠区分时，保留整份日志并在报告里说明。

### 6. 报告

给用户一份短报告，按「移走的内容 → 落点」列出，然后说明丢弃了什么、为什么。未核实的条目单独列出来，不要含糊带过。

## 不要做的事

- 不要把日志内容原样搬进 `docs/`。搬完日志空了，但文档只是多了一份会过期的流水账。
- 不要在 `docs/` 或笔记里链接 `.agents/ops-log.md`。那个文件会被清空，链接会变成死链或指向无关内容。
- 不要为了凑内容给一次性事件建档。日志清空后，这些细节本来就该消失。
- 不要把凭证、令牌、完整对话、机器私有配置写进任何长期文件。

## 判断标准

做完之后问一句：半年后的人读 `docs/` 和 `.agents/notes/`，能不能得到比读日志更准确的结论？如果不能，说明这次蒸馏只是搬运，应该丢掉更多。
