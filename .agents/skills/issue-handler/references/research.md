# 调研：从证据到施工方案

每次使用都重新核对“latest”，不要把这份手册、旧笔记或全局安装版本当作最新版本证明。日期、版本、来源与适用范围一起交给主 agent。

## 共同输入与输出

给每个 explore subagent 同样的 issue、复现、代码基线 SHA、目标版本线、项目定位和约束，再给各自独立问题。三路同批启动，主 agent 在等待时可以做复现、整理验收等独立工作。委派使用当前运行时实际提供的 subagent 接口，不假设某个插件命令已安装。

每路输出：

1. 结论与建议：本项目具体该改什么，或为什么不改。
2. 证据：URL/仓内文件与位置、访问日期、版本/tag/commit；引文足够核对。
3. 事实与推断分开：是否实际复现，是否只有源码依据。
4. 可施工信息：受影响接口、数据流、关键约束、推荐验证。
5. 风险、替代方案和仍缺什么证据。

无法联网、没有 subagent 能力或达到委派深度上限时，明确报告缺失阶段和恢复办法，保留已做工作。主 agent 自查不能冒充用户要求的独立调研或审查；必需角度未执行时不得宣布这一阶段完成。

## 官方文档角度

同时核对两套上游：

- Paseo：从 [官方插件与 Provider 文档](https://paseo.sh/docs/plugins/providers)、官方 SDK 文档和 [provider-direct 示例](https://github.com/getpaseo/paseo/tree/main/plugin-examples/provider-direct) 找当前维护入口与变更。
- DeepSeek Harness：从 [官方仓库](https://github.com/deepseek-ai/deepseek-harness) 的当前文档、发布说明与实际目标 tag 源码核对 API、事件、配置及生命周期。

至少回答：最新文档建议什么；本仓锁定 SDK/DSH 版本实际支持什么；两者有无差异；最低支持版本是否可以降级。记录查询当时的版本和固定提交链接，不能只贴会变化的 main 链接。

最新版本具备某能力，不代表插件最低支持版本也具备。遵守项目的“只在真不兼容时提高下限”规则；若要提高，给出旧版本不可用的实际证据和用户影响。

## 社区经验角度

实际搜索同类 agent/IDE/移动端适配器中的相似问题，结合本 issue 选择关键词：流式事件、终态、取消、审批、子进程、会话恢复、SDK 漂移、插件跨端等。依次优先实现仓库、相关 issue/PR、维护者复盘，再用教程或讨论补充。

至少给出两个可核实的相关来源；找不到时记录检索范围与不足，不编造案例。不为凑数引用无关帖子。给每条经验注明“相同条件 / 不同条件 / 本仓能用的部分”，不能照搬另一项目的 API 或权限方案。

## 项目历史、架构与立项目的角度

实际读取：

- 根规范、当前架构和验收文档、本次涉及的代码与测试。
- 与问题关键词、调用链或设计有关的历史 issue、PR、git history 与决定记录；GitHub 搜索须包含已关闭项，展开关键讨论，分页读取需要的结果。
- 已否决方案、已经被取代的实现和归档材料。历史可以解释理由，当前事实仍以现行规范及代码为准。

说明本仓解决什么连接/呈现问题、哪些责任属于上游、这次修改为何符合定位；不要复活已退役的接单器或把未经认可的草稿当已批准需求。

## 主 agent 综合

不要把三份报告简单拼接。逐项处理冲突，把选定接口、替代方案、实施步骤与验收连起来。每个验收标准都能对应具体实现和验证；还不确定的前置条件必须显式列出。proposal 通过可执行性与可读性审查后，才开始 coding。
