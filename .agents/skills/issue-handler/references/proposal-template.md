# 施工 proposal 模板

这是结构示例，不是已经做出的决定。用实际内容替换占位符。每个 issue 一份综合方案，不把三个 subagent 的报告当三份待实施决定。方向性决定按 [notes 规则](../../../notes/README.md) 选择分类、查重和处理 supersession；普通修复放 `.github/issue-assets/issue-<编号>/proposal.md`，使用下方内容结构但将标题改为 `# Issue #编号: <施工方案标题>`，删除 `Status: proposed` 行，不冒充长期决定。

```markdown
# 决策记录: <动宾结构，说明解决什么问题>

Status: proposed

## 问题

Issue: <本仓 issue URL>
基线: <完整SHA>；目标线: <main 或 rel/major.minor>。

用户看到了什么，什么条件下发生？本项目为什么负责？
预期效果是什么，哪些内容不在本次范围？
规模判断：普通修改 / wait-human，理由及用户影响。

### 三路证据

- 官方：Paseo 与 DSH 当前文档/版本、固定提交、适用接口及降级。
- 社区：相关案例链接、经验与本仓的相同/不同条件。
- 本项目：历史 issue/PR、现行架构、实现位置和项目定位。

列出实际访问日期，区分观察、推断和未知项。写清冲突如何裁决。

## 提案

### 改什么，数据如何流动

<涉及的具体文件、接口/事件/类型、调用方及数据流；必要时附小图。>

### 施工顺序

1. <一项可独立理解的实现，关联位置、约束及验证。>
2. <后续实现及其依赖。>

### 兼容与回退

<最低支持版本、旧版降级、前后端边界、失败/取消/恢复语义。>
<如何撤销候选改动；是否有不兼容数据或部署影响。>

## 考虑过的其他做法

- <方案A>：收益、代价以及没选它的具体理由。
- <维持现状>：影响与本次选择。

## 怎么算做完

- <可复现的行为验收，与实现步骤对应。>
- <相关回归、集成/跨平台验证及所需环境。>
- <待审PR、图解、版本材料与本人逐次确认；无需发包则说明。>

## 风险

<剩余未知项、必须解决的前置条件、未验证平台。>
```

方向性方案完成后，按 notes 规则把本文重写并移到 `implemented/<kind>/`：`提案` 改为当前实现的 `决定`，将验收与风险整理为 `后果`、`怎么验证的`，删除未执行的承诺，修好链接。不改写既有其他决定；发生方向变化时明确 supersession。普通修复的方案不移入 notes，原位补齐实现、验证结果与剩余未验证项。

PR 与 issue 评论负责记录审查、批准和交付状态；方案正文负责解释为什么选择这些代码。图片不得把“候选已验证”画成“用户已经更新”。
