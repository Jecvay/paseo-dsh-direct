# SVG 总结、候选确认与发布

## 图解如何让人判断

以“问题 → 变化 → 结果”为主线，能用箭头说明的关系就不再写一段解释。参考 [模板](../assets/summary.svg)，按实际 issue 重画，不能只把编号和标题换掉。

- 建议 `viewBox="0 0 1600 1000"`，有明确宽高；标题约 42px、框内主词约 28px。逻辑复杂时拆成两张，手机上不能靠不断缩小字体塞进去。
- 上半部画问题发生的条件和造成影响的路径，下半部画修改后的路径；圈出实际变更点，用不同边框区分保持不变的环节。
- 异常、取消、恢复等分支与主线用明确箭头和极少短词表达。线条走向应能跟读，避免交叉、无箭头的线和没有含义的装饰。不依赖动画表达顺序。
- 图上保留用户结果、已测/未测、待确认状态。包、版本、模块名仅在帮助判断时出现；完整 SHA 和命令留在旁边链接中。
- SVG 自包含：使用 `title`、`desc`、基础 shape/path/text 与系统中文字体回退；不含脚本、`foreignObject`、外链图片/字体、网络请求、秘密或主机敏感路径。短 alt 文本说清核心变化。
- 检查 XML 可解析并实际渲染看一眼；检查文字越界、中文缺字、箭头遮挡和手机阅读。用已有轻量渲染工具，打开浏览器检查时及时关闭，不为做图启动长期浏览器进程。

源图放 `.github/issue-assets/issue-<编号>/summary.svg`，可选的 PNG 放同目录。它们是本次变更的审查材料，不随 npm 包发布；不要在 `docs/` 堆“这次改了什么”的历史。

## 在 GitHub 上发布图

1. 图解及必要的版本材料先纳入候选分支，完成 review、测试和 CI，取得最终完整 HEAD SHA。推送范围仅候选分支，不推 `main`、`rel/*` 或 `v*`。
2. 图片必须已存在于 GitHub 可访问的提交。固定 SHA 图片 URL：
   `https://raw.githubusercontent.com/Jecvay/paseo-dsh-direct/<完整SHA>/.github/issue-assets/issue-<编号>/summary.svg`
3. 原图链接用对应的 GitHub `blob/<完整SHA>/…`。先核对图片能匿名获取、内容类型和响应确为图源，再核对 issue 评论实际展示；不能把 HTTP 200 当作已验证视觉效果。
4. GitHub Markdown 不执行内联 `<svg>`，也不会替 `gh issue comment` 自动上传本地附件；本地路径、内网 URL 与 data URL 都不能作为公开图交付。
5. SVG 受 GitHub 代理、净化和客户端差异影响。若内联展示不可靠，用同提交的 PNG 预览并保留 SVG 原图链接。无法得到可靠预览时，留最少文字和 SVG 链接，明确图解展示尚未验收；不能假装已发布成功的大图。

短评论示例（替换占位符再发）：

```markdown
<!-- issue-handler:issue-123:review -->
已修复 <用户可感知的问题>，等待你确认这次交付。

![问题路径与修复后的变化](<固定SHA的SVG或PNG URL>)

[查看SVG原图](<固定SHA的blob URL>) · [PR](<PR URL>) · [方案](<固定SHA的方案URL>) · [验证](<CI及必要验收证据URL>)

候选：`<完整HEAD SHA>` → `main`；版本 `<X.Y.Z>`，npm `latest`。
验证：<通过摘要>；未验证：<实际未验证项或无>。
请确认是否批准这次合并与发布。<若wait-human，补一句具体架构影响。>
```

评论只更新自己创建且可核实身份的同标记评论。标记用于查重，不是权限证明。使用 `gh issue comment --body-file` 或结构化 API 传正文，不把 issue 原文拼进 shell 命令。请求结果不确定时，先分页查询是否已经发出，再决定重试。

## 从审查候选到本人确认

审查对象至少包括 repo、issue、PR、完整 HEAD SHA、base 分支、拟发版本/dist-tag、方案与图解、验证结果及已知风险。用简短可读的正文展示这些信息；黑伤 ask 的 about 只作恢复定位，批准由真实本人的回答提供。

候选的代码、版本、依赖、权限或影响范围实质变化后，需要更新图解、review 和验收，重新取得对应候选的批准。目标分支推进时重新核对差异与 CI；需要 rebase 或修冲突而改变 HEAD 时按新候选重新确认。不能把批准内容与最终合并对象分开。

## 按本仓流程发布

以根 [发布约定](../../../../AGENTS.md#日常-ops)、[开发与验证](../../../../docs/plugin-guide.md#发布验证与排障) 及 [Publish 工作流](../../../../.github/workflows/publish.yml) 为准，每次发布前重新读取。

### 确认前的候选准备

- 判断是否需要 npm 版本：运行时代码/分发产物通常需要；纯 skill、研究或内部文档若不随包分发，则只准备合并，不能为了步骤齐全硬发一个版本。
- 需要发包时，在同一 PR 改 `package.json` 版本、锁文件对应版本字段及 `CHANGELOG.md`；遵守既有版本线。发布 PR 分支用 `issue/…` 或 `release/…`，不能碰巧以 `rel/…` 开头触发维护线发布。
- 目标 `main` 对应当前线与 `latest`；旧线是 `rel/<major.minor>` 与 `dsh-<major.minor>`，不是历史材料中的 `release/<major.minor>`。
- 发布前的版本材料、方案落点调整和图解也应进入最终候选并通过适用检查，再请人确认。

### 收到批准后的执行

1. 核实答复确实批准此候选的合并/发布，并核对当前 PR HEAD、base、版本、工作流、review 和必要 CI。`wait-human` 时确认架构影响包含在同意中，再移除该标签；标签移除本身不代表同意。
2. 先查询该 PR 是否已经合并、该版本是否已经发布、tag 是否已存在，处理好部分成功后的续办。
3. 尚未合并时，使用与批准 HEAD 绑定的合并，例如 `gh pr merge` 的 `--match-head-commit <批准的完整SHA>`。遵守仓库检查与分支保护，不加 `--admin`，不先开启一个会随新提交自动合并的后台流程。
4. 合并到正确版本线会触发现有 Publish；不要另执行 `npm publish` 或手推 tag。手动 dispatch 属于发布动作，也要在该批准范围内。若用户改为手动兜底，严格按根规则从对应 tag 的干净 checkout 执行。
5. 无需发包时，只核实批准的合并确实完成，在评论说明“已合并，无需 npm 发布”。

### 核实实际结果

- 查看此次合并提交对应的 Publish run，区分排队、执行中、失败与成功；不要串到同名的另一轮。可以用现有命令有界等待同一个 run（如 `gh run watch <run-id> --exit-status`），长等待放入可追踪的后台任务，不阻塞沟通。
- 如果黑伤这一轮将结束而 run 仍未完，返回一次性 `later` 回执：`key` 为 `issue-<N>-publish-<run-id>`，`at` 使用实际算出的带时区复查时刻，`about` 带 repo/issue/PR/已批准HEAD/merge SHA/版本/dist-tag/run URL/剩余核验。恢复时只核对同次发布；同 key 已在 waiting 时复用，完成后取消尚存复查。依现有流程预计时长有界复查，长时间无进展时报告实际原因，不能无限循环。手动调用保留运行时能回报结果的后台等待任务。无需为正常执行中的 Publish 再发批准卡，也不能只写“等下次事件”就结束。
- 上述 `later` 用于已批准交付的结果核实；第 9 步等待本人批准、登录或环境恢复时仍按 ask 结束，不安排定时催问。
- 核对 npm 上的精确版本、正确 dist-tag 和 tarball 可获取；核对远端 `vX.Y.Z` 指向本次发布提交。
- 允许短暂的 registry 同步延迟；遇到延迟先查既有结果，不重发包。版本已存在但 tag/dist-tag 不完整时按根工作流的既有修复路径处理。
- 失败或网络结果不确定时，先核实哪个动作已完成。代码修复造成候选变化需重新走审查与确认；不为消除失败改权限、绕测试或跳分支保护。
- 最终 issue 评论和黑伤回执给出实际发布版本、Actions/npm/tag 链接或明确的未完成项；已合并与已发布分别表述。
